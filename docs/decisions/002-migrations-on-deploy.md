# 002 — Run migrations on deploy

- **Status:** Accepted
- **Date:** 2026-10-11

## Context

- Migrations are SQL files in `src/server/db/migrations/`, generated by `npm run db:generate`.
- Locally we apply them to the Neon `dev` branch with `npm run db:migrate`.
- The production database (Neon `main` branch) needs the same migrations, and they must be applied **before** the new code that depends on them goes live.
- Running them by hand is easy to forget.

## Decision

Vercel runs the migrations as part of the **production** build (`vercel.json`):

```sh
if [ "$VERCEL_ENV" = "production" ]; then npm run db:migrate; fi && npm run build
```

- **Production deploys** (merge to `main`): migrate the production database, then build.
- **Preview deploys** (every PR): build only. They never change a database.
- Vercel's `DATABASE_URL` is set per environment: Production → Neon `main`, Preview → Neon `dev`.

## Alternatives considered

- **A GitHub Actions job on merge to `main`.** It runs at the same time as the Vercel deploy, so new code could go live before its tables exist. It would also need a second copy of the production secret in GitHub.
- **Running migrations by hand.** Easy to forget, and there's no record of when it happened.

## Consequences

- **Good:**
  - Migrations always run before the new code is served.
  - If a migration fails, the build fails and the previous version keeps running.
  - The production database URL lives in one place (Vercel).
- **Costs:**
  - A migration must not break the code that is still live while the build runs. For a risky change, such as renaming or dropping a column, split it across two PRs: first add the new column, then remove the old one later.
  - Preview deploys don't get the PR's new tables. A PR that needs them to work on its preview must be migrated to `dev` by hand (`npm run db:migrate`).
- **Revisit if:**
  - We need each PR preview to have its own database (Neon can create a branch per preview).
